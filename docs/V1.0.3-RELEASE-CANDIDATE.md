# DepoAudio v1.0.3 release candidate

Status: **NO-GO for publication; private RC evidence only**

Reviewed: 2026-08-29

Initial RC evidence base: `49fd2e06c246db426c0f69411c7b24536907e455`

Latest verified published release: `v1.0.2`

This document separates a buildable v1.0.3 source candidate from a verified,
downloadable release. Version metadata and change notes may be merged before a
private candidate is built. The private application candidate correctly
reports 1.0.3, while the README published-release badge and website must
continue to describe v1.0.2 until v1.0.3 is published and its assets are
independently checked.

The v1.0.3 changelog heading remains `Unpublished` during candidate work.
The private-draft build workflow is allowed to run while the status remains
`NO-GO` so that it can collect exact artifact evidence. Publication is a
separate operation: before publication, replace the marker with the approved
release date, close every machine-readable blocker, bind the exact private
draft receipt, and change this document's reviewed status to
`GO for publication`. A buildable source tree or green private draft is not
publication approval.

## Intended scope

- Add an accessible, local-only root React recovery screen for unhandled
  interface rendering and lifecycle failures.
- Enforce deterministic frontend size budgets.
- Enforce Cargo license, source, wildcard, and dependency policy across the
  configured release targets.
- Revalidate the complete npm, Cargo, Tauri, and changelog version contract at
  the start of the release workflow.
- Update `plist` and `quick-xml` to remove `RUSTSEC-2026-0194` and
  `RUSTSEC-2026-0195` from the locked graph.
- Record native, installer, fixture, JavaScript-notice, and model non-distribution evidence that must
  be reviewed before publication.
- Ship v1.0.3 with zero learned-model weights or execution paths. Remove the
  bundled ONNX files, embedded RNNoise weights, ONNX Runtime, model downloads,
  and learned cleanup/analysis controls. Existing app-data copies remain
  visible only for user-initiated deletion and are never loaded.
- Replace the macOS community FFmpeg binaries that identified themselves as
  nonfree/unredistributable with same-version Apple Silicon and Intel builds
  from a hash-pinned LGPL FFmpeg/LAME/Opus source set. Use the reviewed BtbN
  LGPL variant on Windows and preserve distribution evidence on both.
- Improve the existing workflows without expanding their capability boundary:
  add normal-shell landmarks and labels, concise failure summaries with
  retained technical detail, status/progress semantics, reduced-motion
  behavior, and compact minimum-window reflow.
- Describe channel splitting and microphone balancing without implying speaker
  identity; fail visibly when approved external trust actions are unavailable;
  and bound transcript lookup and autosave work while retaining
  a recoverable in-session draft after local storage failures.
- Preserve the v1.0.2 capability boundary. No format, conversion, cleanup,
  model, player, library, Merge, or transcript capability is added.

## Machine-readable publication gate

[`V1.0.3-RELEASE-GATE.json`](V1.0.3-RELEASE-GATE.json) is the fail-closed
publication contract. While it is `NO-GO`, its candidate receipt fields may be
empty and the private-draft workflow may collect evidence. Publication requires
all of the following in the committed gate:

- status `GO` and zero open blockers, with named reviewers and retained evidence
  references for every closure;
- the exact private GitHub release ID, full source commit, tag, and a reviewed
  deterministic asset-manifest SHA-256;
- an explicit updater decision (`signed` or `unavailable`), the exact
  Tauri-config public-key value when signed, the actual publication date, and a
  named approver; and
- a changelog heading whose date exactly matches the approved publication date.

`npm run release:check` validates the normal private-candidate state. The
publication-only workflow must additionally run
`node scripts/release-contract-check.mjs --publication-ready`; that mode rejects the
current `NO-GO` state by design.

### Exact candidate-to-publication sequence

Publication uses two intentionally distinct commits. The **source commit** is
the commit that built the immutable installers and remains the public release
tag target. A later **approval commit** closes the evidence gate, dates the
changelog, and records the exact private-draft receipt. The generated
`RELEASE-APPROVAL.json` binds both commits plus the workflow actor and run.

1. Merge the intended source to `main`, confirm the five private FTR fixture
   secrets are configured, and dispatch the build-only workflow:

   ```bash
   gh workflow run release.yml --ref main -f tag=v1.0.3
   ```

2. Let it create and verify one commit-bound **private** `v1.0.3` draft. Do not
   use GitHub's Publish button, move the tag, replace an asset, or reuse RC1.
3. Record that draft's numeric release ID and exact build commit in
   `candidate.releaseId` and `candidate.sourceCommit`, leaving the gate
   `NO-GO`. Commit those receipt fields to `main`.
4. From that exact `main` commit, run the read-only inspection:

   ```bash
   gh workflow run publish-release.yml --ref main \
     -f operation=inspect -f 'confirmation=INSPECT v1.0.3'
   ```

5. Download the `release-candidate-inspection-*` workflow artifact. Review the
   complete asset inventory and retain its canonical
   `PREPUBLICATION-ASSET-MANIFEST.txt`; copy the reported SHA-256 into
   `candidate.assetManifestSha256` only after the assets and all evidence files
   are accepted.
6. Complete clean installed-app, upgrade, signing, license, model, fixture,
   codec/patent, and updater review. Close each blocker with a closure date,
   accountable reviewer, and durable evidence references.
7. Set `candidate.updater` to `signed` or `unavailable`. For `signed`, set
   `candidate.updaterPublicKey` to the exact outer-base64 public-key value used
   by the Tauri updater configuration; never commit the private key. For
   `unavailable`, keep the public key `null` and require zero updater signature
   assets.
8. Set the changelog and `candidate.publicationDate` to the current UTC date,
   name `candidate.approvedBy`, change both human and machine status to `GO`,
   and commit that approval state to `main`. The date guard intentionally
   requires a new approval commit if protected-environment review crosses UTC
   midnight.
9. Before the first publish run, configure the GitHub environment
   `release-publication` with required reviewers, prevent self-review, and limit
   deployment to `main`. Repository YAML cannot prove or enforce these
   dashboard settings by itself. The publication workflow also reads the public
   environment contract and fails before checkout unless it finds at least one
   required reviewer, `prevent_self_review=true`, custom deployment branch
   policies, and exactly one allowed branch named `main`. As reviewed on
   2026-08-26, only the unrelated `Production` environment exists, so
   publication remains blocked until this setup is completed and rechecked.
10. While that approval commit is still `main`, dispatch publication:

    ```bash
    gh workflow run publish-release.yml --ref main \
      -f operation=publish -f 'confirmation=PUBLISH v1.0.3'
    ```

11. The protected workflow checks out the immutable dispatch SHA, verifies the
    GO contract and every downloaded asset, validates updater signatures when
    enabled, attaches the approval receipt and optional `latest.json`, binds or
    verifies the tag at the source commit, and publishes only the exact release
    ID. It never builds, deletes, or replaces an installer.
12. Confirm the public assets are downloadable and install-smoke them again.
    Only then update and merge the website release contract, visible changelog,
    structured data, and direct download links.

## Permission-cleared private FTR release fixture

The release workflow no longer contains or downloads a public courtroom-audio
sample. Before a release run, configure all five values as GitHub Actions
repository secrets. If they are later moved to a protected GitHub environment,
both the `prepare` and `release` jobs must explicitly reference that environment:

| Secret                      | Required value                                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `FTR_FIXTURE_URL`           | Direct HTTPS location for the access-controlled fixture. Redirects fail closed; do not embed credentials in the URL.                           |
| `FTR_FIXTURE_AUTHORIZATION` | Complete HTTP `Authorization` value used only for the fixture request.                                                                         |
| `FTR_FIXTURE_SIZE`          | Exact positive byte count for the approved fixture.                                                                                            |
| `FTR_FIXTURE_SHA256`        | Exact 64-character SHA-256 digest for the approved bytes.                                                                                      |
| `FTR_FIXTURE_EVIDENCE_ID`   | Identifier for the separately retained, owner-approved provenance and permission record. It must not contain recording content or credentials. |

That evidence record must identify who created or supplied the fixture, whether
it is synthetic or de-identified, the confidentiality review performed, and
permission for private automated CI use. A secret or hash proves neither
ownership nor permission. Do not place the recording, its locator, its digest,
case metadata, or the authorization value in source, logs, issues, release
assets, or public CI artifacts.

`scripts/private-ftr-fixture.mjs` fails before release preparation when any
secret is absent or malformed. Each platform then streams only the declared
number of bytes, verifies SHA-256, runs the FTR decoder/encoder smoke, and
removes the fixture before packaging. Final installer inventory also rejects
every `.trm` file. If the owner-approved record cannot be supplied, do not
approve publication; retain FTR verification as a private manual gate.

## WebView2 build-input evidence boundary

Tauri CLI 2.11.4 includes tauri-bundler 2.9.4. Its
[offline-installer helper](https://github.com/tauri-apps/tauri/blob/tauri-bundler-v2.9.4/crates/tauri-bundler/src/bundle/windows/util.rs)
resolves Microsoft's moving x64 fwlink before selecting a GUID/filename cache
path. The
[NSIS bundler](https://github.com/tauri-apps/tauri/blob/tauri-bundler-v2.9.4/crates/tauri-bundler/src/bundle/windows/nsis/mod.rs)
can reuse `%LOCALAPPDATA%\tauri\x64\<GUID>\<filename>`, but still performs
that moving resolution. The
[WiX bundler](https://github.com/tauri-apps/tauri/blob/tauri-bundler-v2.9.4/crates/tauri-bundler/src/bundle/windows/msi/mod.rs)
deletes and recreates its output directory before downloading its own copy.
There is no supported `offlineInstaller` path field.

For that reason, this release does not claim deterministic WebView2 pre-seeding.
`scripts/windows-webview2-evidence.ps1` instead fails the Windows build unless
the WiX and NSIS inputs resolve to the same GUID/filename, have identical size
and SHA-256, and validate as Microsoft-signed. It uploads a JSON input manifest
and sanitized `signtool` report to the private draft. The manifest explicitly
sets `finalInstallerEmbeddingVerified` to `false`: final approval still requires
extracting the MSI Binary table and NSIS payload, matching the recorded digest,
and reviewing the exact Microsoft terms.

A private candidate draft may be used to collect evidence. It is not
publication approval. Before publishing a final release:

1. Confirm the workflow ran from the exact intended `main` commit.
2. Record each asset name, byte size, SHA-256 digest, and download URL.
3. Verify Windows 10/11 x64 installation and startup for both MSI and NSIS.
4. On a clean Windows system without WebView2, confirm both installers install
   the runtime and start DepoAudio. Extract the MSI Binary table and NSIS
   payload and match the workflow's recorded WebView2 SHA-256.
5. Verify macOS 13.3+ startup on Apple Silicon and Intel.
6. Verify Authenticode, Apple signing, notarization, Gatekeeper, SmartScreen,
   updater metadata, and updater signatures from the built assets themselves.
7. Exercise file opening, non-learned conversion, playback, library, transcript,
   and legacy-model deletion on the installed applications. Confirm the app
   exposes no learned cleanup, analysis, install, or download controls.
8. Confirm optional network behavior and that recordings are not uploaded.
9. Upgrade an existing v1.0.2 installation through MSI, NSIS, and macOS paths;
   prove old bundled model resources are absent from v1.0.3, existing app-data
   model files are never loaded or advertised, and an exact legacy regular file
   remains user-controlled and deletion-only.
10. Replace the generic draft body with release notes grounded in the tested
    artifacts.

Only after the final v1.0.3 release is public and install-smoked should the
website release contract, direct downloads, changelog, structured data, and
published-release badge be updated and merged.
