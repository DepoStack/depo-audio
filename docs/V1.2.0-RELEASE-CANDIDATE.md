## Intended scope

v1.2.0 is the first release since v1.0.2. It contains everything merged to
`main` since the `v1.0.2` tag (`git log v1.0.2..origin/main`): the work
prepared for the never-published v1.0.3 and v1.1.0, and the format, Player and
safety work merged after the v1.1.0 candidate was built. The `## [1.2.0]`
changelog section is the user-facing list. In short:

- **Formats.** New readers built from owner-supplied interoperability notes:
  DigitalCAT / SoundSync `.dm` (with `.bmf` marker counts), Liberty / BIS
  Digital `.dcr` (redactions applied, sealed audio silent), an FTR route that
  splits channels itself when FFmpeg's decoder cannot read a file (damaged
  rounds filled, start time kept, `.tll` accepted), and SGMCA Direct Audio read
  and written natively with every recording session. These four are
  **Preview**: tested with synthetic samples only. Also: audio from older
  deposition video containers, recognition of closed formats (DS2, Webex,
  Sony) with export-first guidance, and RF64 headers for WAV outputs over
  4 GiB.
- **Player and proofing.** Three-pane Player; transcript proofing against the
  audio (SRT, WebVTT, CAT ASCII/TXT) with flags for review and CSV/text export,
  replacing the old transcript editor; Backstep; volume; Separate channels with
  Mute, Solo and per-channel volume; playback keys while typing in another app
  (off by default); Compare with original.
- **Safety for legal audio.** An export record (`<output>.depoaudio.json`)
  beside every converted file; BWF start time carried through; checks that
  outputs keep every sample in place (limiter delay compensated, trim at the
  first sample over the threshold, Keep Original refuses lossy formats that
  would drop channels, the first audio track always named); temporary audio
  in a private per-run work folder; Settings → Your data (backup, import,
  clear all); Copy diagnostics with no file names or paths.
- **Build and release.** macOS FFmpeg built from a hash-pinned LGPL FFmpeg
  7.1.5, LAME 3.100 and Opus 1.6.1 source set; the reviewed BtbN LGPL FFmpeg
  build on Windows; Tauri 2.12.5 and updater plugin 2.14.1 with the Visual C++
  runtime still linked dynamically on Windows; Windows installers built on the
  self-hosted runner by default (#211, `windows_runner` input); no Rust
  advisory exception (`cookie` 0.18.3, #221); the bundled Archivo and Fragment
  Mono typefaces; the fail-closed release workflow and publication gate.
- **Still excluded.** Learned-model processing: v1.2.0 ships zero models, and
  local AI is planned for v2. The hidden Merge workflow, whose commands stay
  off the IPC surface.

### Exact candidate-to-publication sequence

Publication uses two intentionally distinct commits. The **source commit** is
the commit that built the immutable installers and remains the public release
tag target. A later **approval commit** closes the evidence gate, dates the
changelog, and records the exact private-draft receipt. The generated
`RELEASE-APPROVAL.json` binds both commits plus the workflow actor and run.

1. Merge the intended source to `main` (this release preparation and any
   change still landing for v1.2.0), wait for CI to pass on that merge commit,
   confirm the synthetic FTR fixture self-test passes, confirm the Apple and
   Windows signing secret groups are unset (signing is off for v1.2.0), and
   dispatch the build-only workflow:

   ```bash
   gh workflow run release.yml --ref main -f tag=v1.2.0 -f windows_runner=self-hosted
   ```

   Use `-f windows_runner=github-hosted` if the self-hosted runner is not
   available; record which one built the candidate.

2. Let it create and verify one commit-bound **private** `v1.2.0` draft. Do not
   use GitHub's Publish button, move the tag, replace an asset, or reuse any
   v1.0.3 or v1.1.0 draft. Check the run log for the signing and updater
   notices the `signing-notarization-and-updater-decision` and
   `updater-keys-or-unavailable` blockers require.
3. Record that draft's numeric release ID and exact build commit in
   `candidate.releaseId` and `candidate.sourceCommit`, leaving the gate
   `NO-GO`. Commit those receipt fields to `main`.
4. From that exact `main` commit, run the read-only inspection:

   ```bash
   gh workflow run publish-release.yml --ref main \
     -f operation=inspect -f 'confirmation=INSPECT v1.2.0'
   ```

5. Download the `release-candidate-inspection-*` workflow artifact. Review the
   complete asset inventory and retain its canonical
   `PREPUBLICATION-ASSET-MANIFEST.txt`; copy the reported SHA-256 into
   `candidate.assetManifestSha256` only after the assets and all evidence files
   are accepted.
6. Complete clean-machine install, upgrade from v1.0.2, signing decision,
   license, font, model, format-reader rights, Preview-format, synthetic-FTR
   decode and cleanup, codec/patent, and updater review. Close each blocker
   with a closure date, accountable reviewer, and durable evidence references.
7. Set `candidate.updater` to `signed` or `unavailable` as described in
   [Updater: two valid outcomes](#updater-two-valid-outcomes).
8. Set the changelog and `candidate.publicationDate` to the UTC date on which
   the publish job will run, name `candidate.approvedBy`, set
   `candidate.releaseTaggerEmail` to the email address the release owner signs
   the tag with (step 10; a GitHub noreply address works, and the tag shows the
   address publicly either way), change both human and machine status to `GO`,
   and commit that approval state to `main`. The job starts only after the
   environment's wait timer (step 9), so the date to record is the UTC date of
   the dispatch time in step 11 **plus the configured wait timer**: the next UTC
   day for exactly 1440 minutes, later for a longer timer. Queueing and setup add
   minutes, so dispatch well clear of UTC midnight (for a 1440-minute timer,
   between about 01:00 and 22:00 UTC). The date guard intentionally fails the
   job, before any release write, if the run lands on a different UTC date, and
   its error names the date the run actually saw; commit a corrected date and
   dispatch again, which costs another full wait.
9. Before the first publish run, the release owner configures three GitHub
   settings by hand (`release-publication-environment-and-tag-ruleset`).
   Repository YAML cannot set them, so the workflow reads them back and fails
   before any release write unless all three hold. No second reviewer is
   required, so one person can complete the release.
   - **Environment `release-publication`:** a wait timer of at least 1440
     minutes (24 hours), "Allow administrators to bypass configured protection
     rules" turned **off**, and deployment limited to the single branch `main`.
     GitHub lets administrators skip the wait timer by default; the job fails
     unless that bypass is off, so nobody, including someone holding an admin
     or stolen owner token, can skip the cancellation window. The job reads
     this as the environment's `can_admins_bypass` field, which must be
     `false`, and fails closed if it is absent. Required reviewers are optional
     and not checked.
   - **Tag ruleset:** an active tag ruleset that includes `refs/tags/v*` and
     turns on "Restrict creations", "Restrict updates" and "Restrict
     deletions", with only the release owner (repository admin) on the bypass
     list. Nobody else can then create a release tag, and nobody can move or
     delete one once it exists. The job checks the rules, but it can check the
     bypass list only if GitHub shows it to the workflow token (not confirmed;
     GitHub may hide it from tokens without admin rights). When the list is
     shown, the job rejects apps, deploy keys and teams on it; it still cannot
     tell which repository role is listed or who holds it. Keeping the bypass
     list to the release owner is therefore a dashboard setting the owner keeps
     by hand, and the job log says whether the list was visible.
   - **Signing key:** the SSH or GPG key used for `git tag -s` is added to the
     release owner's GitHub account as a signing key, and the email recorded in
     `candidate.releaseTaggerEmail` is a verified email on that account.
     GitHub then reports the tag as verified, and the job checks that the
     tagger, in the tag object and in the signed payload, is that email. A tag
     signed with a key on any other account, or with another tagger email,
     fails.

   The publish job has never run, so none of these settings has yet been
   confirmed by a run. Publication stays blocked until they are set up and a
   run confirms them.

10. Create the signed annotated tag at the exact candidate source commit, check
    it locally, and push it (`signed-release-tag`). `release.yml` refuses to
    build when the tag already exists, so do this only after the candidate is
    built and recorded. The tagger email (`git config user.email`) must equal
    `candidate.releaseTaggerEmail`:

    ```bash
    git fetch origin
    test "$(git config user.email)" = "$(node -p "require('./docs/V1.2.0-RELEASE-GATE.json').candidate.releaseTaggerEmail")"
    source_commit=$(node -p "require('./docs/V1.2.0-RELEASE-GATE.json').candidate.sourceCommit")
    git tag -s v1.2.0 "$source_commit" -m 'DepoAudio v1.2.0'
    git tag -v v1.2.0
    git push origin refs/tags/v1.2.0
    ```

11. While that approval commit is still `main`, dispatch publication:

    ```bash
    gh workflow run publish-release.yml --ref main \
      -f operation=publish -f 'confirmation=PUBLISH v1.2.0'
    ```

    The job waits for the environment's wait timer (at least 24 hours,
    `publication-24h-hold`) before it starts, and administrators cannot skip
    that wait. To stop the release, cancel the run during that time; nothing
    has been written yet.

12. The protected workflow checks out the immutable dispatch SHA, verifies the
    wait timer and its administrator bypass setting, deployment branch, tag
    ruleset, verified tag signature and tagger email,
    verifies the GO contract and every downloaded asset, validates updater
    signatures when enabled, attaches the approval receipt and optional
    `latest.json`, re-verifies the signed tag at the source commit, and
    publishes only the exact release ID. It never builds, deletes, or replaces
    an installer, and it never creates, moves, or deletes a tag.
13. Confirm the public assets are downloadable and install-smoke them again.
    Only then update and merge the README published-release badge and release
    truth, the website release contract, visible changelog, structured data,
    and direct download links.

The concurrency group and the two confirmation strings in
`publish-release.yml` are evaluated before checkout, so they name `v1.2.0`
literally; `npm run release:check` fails if they stop matching
`package.json`'s version.

## Generated synthetic FTR decode fixture

The release workflow does not download or require a private courtroom
recording. `scripts/ftr-smoke-fixture.mjs` creates a deterministic mono 440 Hz
PCM WAV under `RUNNER_TEMP/depoaudio-ftr-smoke`, uses the exact candidate FFmpeg
to encode AAC and mux an AVI with the FFmpeg 7.1.5-compatible ADTS audio format
tag `0x1600`, then changes that tag to FTR `0x4180`. The result contains no
voice, case metadata, or user-supplied recording content and requires no
fixture credentials.

The generated file is a narrow normal-decode smoke input; it does not claim to
represent every vendor-produced FTR recording or replace broader compatibility
testing. Each platform must prove that the exact candidate ffprobe and FFmpeg
sidecars recognize and decode it through the released FTR path. The helper
keeps the fixture and derived outputs in the runner's temporary directory and
removes them before packaging. Installer and release-asset inventories
continue to reject every `.trm` file and must also show that no derived
smoke-test output was packaged.

Publication remains `NO-GO` until the exact candidate evidence proves both the
decode and cleanup requirements. A source-level helper self-test alone does not
close this gate.

## WebView2 build-input evidence boundary

v1.2.0 is built with Tauri CLI 2.12.4, which pins tauri-bundler 2.10.4. On
2026-11-12 the published tauri-bundler 2.9.4 (which built the v1.0.3
candidate) and 2.10.4 crate sources were compared:
`download_webview2_offline_installer`, the Microsoft x64 fwlink, the
GUID/filename path resolution, the WiX `wix/<arch>` delete-and-recreate step,
and the NSIS `%LOCALAPPDATA%\tauri\<arch>` cache are unchanged, so
`scripts/windows-webview2-evidence.ps1` expects CLI 2.12.4 with the same paths.
Bundler 2.10.4 does change other installer inputs: it downloads NSIS 3.13
instead of 3.11 and can bundle Visual C++ runtime DLLs when
`bundle.windows.bundleVCRuntime` is set (DepoAudio does not set it).

Tauri 2.12 also changes how the app binary itself is linked: `tauri-build`
2.7.4 statically links the Microsoft Visual C++ runtime into `depo-audio.exe`
unless `build.windows.staticVCRuntime` is `false`. `tauri.conf.json` sets it to
`false`, so the app keeps loading the runtime DLLs installed on the machine, and
`npm run release:check` fails if that setting changes. The clean-install tests
on fresh Windows 10 and 11 machines must confirm the app starts there.
Embedding the runtime instead is an owner decision that also needs a ledger
entry and a redistribution review.

The [offline-installer helper](https://github.com/tauri-apps/tauri/blob/tauri-bundler-v2.10.4/crates/tauri-bundler/src/bundle/windows/util.rs)
resolves Microsoft's moving x64 fwlink before selecting a GUID/filename cache
path. The
[NSIS bundler](https://github.com/tauri-apps/tauri/blob/tauri-bundler-v2.10.4/crates/tauri-bundler/src/bundle/windows/nsis/mod.rs)
can reuse `%LOCALAPPDATA%\tauri\x64\<GUID>\<filename>`, but still performs
that moving resolution. The
[WiX bundler](https://github.com/tauri-apps/tauri/blob/tauri-bundler-v2.10.4/crates/tauri-bundler/src/bundle/windows/msi/mod.rs)
deletes and recreates its output directory before downloading its own copy.
There is no supported `offlineInstaller` path field.

For that reason, this release does not claim deterministic WebView2 pre-seeding.
`scripts/windows-webview2-evidence.ps1` instead fails the Windows build unless
the WiX and NSIS inputs resolve to the same GUID/filename, have identical size
and SHA-256, and validate as Microsoft-signed. It uploads a JSON input manifest
and sanitized `signtool` report to the private draft. The manifest explicitly
sets `finalInstallerEmbeddingVerified` to `false`: approval still requires
extracting the MSI Binary table and NSIS payload, matching the recorded digest,
and reviewing the exact Microsoft terms.
